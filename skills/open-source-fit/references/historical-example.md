# 历史案例：从开源调研回到现有原型

这是根据用户既有调研对话抽象的匿名案例，用于展示方法。产品版本、许可、收费、源码行为和可用性必须在新任务中重新核验，不继承当时结论。

## 当时的问题

一个已有 Node.js 原型的销售项目，需要客户跟进、记录授权、到店定位、照片留证、弱网保存和报销资料包。长期可能扩展 ERP、CRM、财务与商城；当前希望先评估免费公开方案，讨论后再实施。

## 实际如何判断

1. 从用户提供的代码托管站、开源替代目录和精选社区寻找候选，按 CRM 系统、开发底座、语音和 OCR 组件分别查看。
2. 回到官方仓库、文档与许可，发现部分产品的关键身份、权限或初始化材料存在付费边界；不能只凭“开源”标签判断。
3. 对芋道两个版本，比较单体/微服务运行方式与新增运维工作，再对照当前项目；多家公司并不自动要求微服务。
4. 阅读与业务最相关的权限、跟进、文件和通知源码；能学习其机制，但还需核对负责人移交后的访问、附件下载、长期业务幂等等差异。
5. 检查集团方案时，识别同一后台下的 CRM 与 ERP 客户实体仍可能独立；需要验证编码和业务联动。
6. 给出保留原型局部优化与采用新后台底座的路线，说明迁移代价。后续在获授权后保留原型，借鉴模块边界、权限、跟进、文件和操作记录机制。

## 可复用的经验

“值得借鉴”是有效采用方式。不同语言不能直接拼接；成熟的模块也可能不符合当前业务规则。先完成本阶段业务闭环，再评估更大范围的技术替换。

关键问题应成为验证场景：谁能查看某条客户记录和附件、权限撤销后是否立即生效、重复操作是否生成重复业务记录、订单与库存和财务是否真正一致。
